# Transfer Radar

海外サッカーの移籍市場を、**独自の移籍確度（0–99%）**付きで一覧するサイト。
プレミアリーグ全クラブ／他リーグのビッグクラブ／日本人選手の海外移籍の3カテゴリ。

- 依存パッケージ **なし**（Node 標準機能のみ）。ビルド工程もなし。
- サイト本体は `data/transfers.json` を読むだけの静的サイト。
- データは Claude の定期タスクが1時間ごとに書き換える。

---

## 起動

```bash
node scripts/serve.mjs
```

→ http://localhost:5173/

`index.html` を直接ダブルクリックしても動きません（`fetch()` が `file://` では
ブロックされるため）。必ず上のサーバー経由で開いてください。

## 構成

> クローンする場所は OneDrive / Dropbox 等の同期フォルダの**外**にしてください。
> 1時間ごとにコミットが増えるため、同期処理と競合して `.git` が壊れることがあります。

```
transfer-radar/
├── index.html              画面
├── robots.txt              クローラ設定
├── .nojekyll               GitHub Pages で Jekyll を通さない
├── assets/style.css        見た目（ライト/ダーク両対応）
├── assets/app.js           描画・絞り込み・並べ替え。CLUB_COLORS もここ
├── data/transfers.json     ★ 移籍データ。定期タスクがこれを書き換える
├── data/photos.json        選手写真のメタ情報（撮影者・ライセンス・生年月日）
├── data/photos/            選手写真の実ファイル
├── scripts/fetch-photos.mjs  Wikimedia から写真と生年月日を取得
├── scripts/serve.mjs         依存ゼロの静的サーバー（ローカル確認用）
├── scripts/deploy.mjs        検証 → commit → push（公開反映）
├── scripts/setup-github.mjs  公開のための一度きりの設定
└── UPDATE_TASK.md          ★ 定期タスクが読む手順書（確度ルーブリックの正本）
```

## 選手写真の扱い

`scripts/fetch-photos.mjs` が Wikipedia / Wikimedia Commons から取得します。

```bash
node scripts/fetch-photos.mjs          # 未取得の選手だけ
node scripts/fetch-photos.mjs --force  # 全選手を取り直す
```

このスクリプトは以下を守っています。

- **commons.wikimedia.org 上のファイルのみ採用。** 英語版 Wikipedia ローカルの
  ファイルはフェアユースの可能性があるため除外します。
- ライセンス名に `fair use` / `non-free` を含むものは除外。
- **撮影者名・ライセンス名が取れない画像は使いません**（帰属表示ができないため）。
- 取得した撮影者・ライセンス・ライセンスURL・Commons のファイルページURLは
  `photos.json` に保存され、各カードの下部に必ず表示されます。
- 写真が無い選手はクラブカラーのグラデーション + イニシャルで表示します。

Wikimedia は匿名アクセスにレート制限（HTTP 429）をかけます。スクリプトは
`Retry-After` を尊重して最大4回まで再試行し、1人あたり約0.7秒空けて進みます。
30人ぶんで10分前後かかります。

> `scripts/fetch-photos.mjs` の `UA` 定数は連絡先を含む文字列に書き換えることを
> Wikimedia が推奨しています。多用する場合は自分のメールアドレス等を入れてください。

年齢は `transfers.json` に書きません。Wikidata の生年月日（P569）から
表示時に計算します（推測値が混ざるのを防ぐため）。

## 1時間ごとの更新

`UPDATE_TASK.md` が定期タスクの手順書です。確度ルーブリック、出力する JSON の
形、禁止事項（推測で数値を埋めない等）がすべてそこに書かれています。
ルーブリックを変えたいときは `UPDATE_TASK.md` と `index.html` の「確度の付け方」
セクションの**両方**を直してください（表示と実装が食い違わないように）。

### スケジュール

Claude Code の定期タスク `transfer-radar-update` として登録済みです。

| 項目 | 値 |
| --- | --- |
| cron | `0 16-23,0-9 * * *`（ローカル時刻 = JST） |
| 稼働時間帯 | **JST 16:00 〜 翌 09:00** の1時間ごと（1日18回） |
| 休止時間帯 | JST 10:00 〜 15:59 |
| タスク定義 | `~/.claude/scheduled-tasks/transfer-radar-update/SKILL.md` |

休止時間帯を設けているのは、そこが CET の深夜〜早朝（欧州の報道が動かない時間）に
当たるためです。JST 16時は CET 09時ごろで、ここから欧州の報道が動き始めます。

**サイト側もこの時間帯を知っています。** `transfers.json` の `updateSchedule.activeHours`
を見て、休止中は「更新が止まっている」警告を出さず、次に再開する時刻を表示します。
cron を変えたら `updateSchedule.activeHours` も合わせて直してください。

> ⚠ **定期タスクは Claude Code アプリが開いている間だけ動きます。** アプリを閉じている
> 間に実行時刻が来た場合は、次にアプリを起動したときに1回だけ実行されます。
> PCを閉じて寝ると朝は最新になっていない、という挙動になります。

24時間動かしたい場合は cron を `0 * * * *` に、さらに頻度を落としたい場合は
`0 16,20,0,4,8 * * *`（4時間ごと）などに変更してください。逆に上げたい場合は
`0,30 16-23,0-9 * * *`（30分ごと）に戻せます。停止・一時停止はサイドバーの
「Scheduled」から行えます。

**cron を変えたら、次の3箇所も必ず合わせてください**（ズレるとサイトが誤った
カウントダウンや誤警告を出します）:

| 場所 | 直すもの |
| --- | --- |
| `data/transfers.json` | `updateSchedule.intervalMinutes` と `activeHours` |
| `assets/app.js` | `UPDATE_INTERVAL_MIN` と `STALE_AFTER_MIN`（間隔の2.5倍が目安） |
| `UPDATE_TASK.md` | §0 の「次の実行が◯後にある」と、`nextUpdateAt` の計算式 |

### 使用モデルとトークン節約

定期タスクの `SKILL.md`（`~/.claude/scheduled-tasks/transfer-radar-update/SKILL.md`）の
frontmatter で指定しています。

```yaml
model: sonnet
effort: medium
```

ルーブリックに沿った確度の判定と日本語要約という定型作業なので Sonnet で足ります。
判断の質が落ちたと感じたら `opus` に、もっと安くしたい場合は `haiku` に変えられます。
ただし Haiku は「相反する報道が並んでいるときに上振れさせない」といった判断が
弱くなる可能性があります。

**さらに効くのがデータの読み方です。** `data/transfers.json` は200KB超
（≒7万トークン）あり、これを毎回読むと1日18回で130万トークンが読み込みだけで消えます。
そのため定期タスクには**このファイルを直接読ませていません**。

| コマンド | 用途 | サイズ |
| --- | --- | --- |
| `node scripts/index.mjs` | 1行1件の一覧。既存案件の把握はこれで足りる | 約18KB（≒6千トークン） |
| `node scripts/index.mjs --id <id>` | 1件だけ全文で確認 | 数百バイト |
| `node scripts/upsert.mjs <配列.json>` | **変更した案件だけ**を反映 | — |

`upsert.mjs` が検証・クラブ名の正規化・重複判定・`generatedAt` の更新をまとめて行うので、
タスク側はファイル全体を組み立てる必要がありません。

### 実行の上限

1回の実行あたり Web検索12件 / WebFetch 6ページ / 最大5分を上限にしています。
これは `UPDATE_TASK.md` の §0 で指示されており、定期実行が無制限に
コストを膨らませないための歯止めです。1日18回動くので、上限を緩めると
その分そのまま利用量に跳ね返ります。

### 手で更新したいとき

Claude Code で次のように頼めば、定期タスクと同じことを1回だけ実行します。

```
transfer-hub/UPDATE_TASK.md の手順で data/transfers.json を更新して
```

## 確度（0–99%）について

このサイトの数字は**独自の推定値**です。移籍成立の確率を示す公的な指標は
存在しません。`UPDATE_TASK.md` §3 のルーブリック（交渉段階でベースを決め、
ソースの信頼度と加減算で補正する）に沿って機械的に算出しています。

- **推定値の上限は 99%。** まだ噂である限り 100% にはなりません。
- **100% はクラブが公式発表した案件だけ**（`status: "成立"`）。確度の推定対象外で、
  「成立」バッジ付きで表示されます。100% だけが推定ではなく事実です。
- 各カードの「この確度の根拠」を開くと、どの帯から何を加減算したのかが見えます。

## 著作権・ライセンスについて

- 選手写真は Commons の自由ライセンス画像のみ。撮影者とライセンスをカードに表示。
- **クラブのエンブレム／ロゴは使っていません。**（ほぼすべて著作権と商標の対象で、
  自由ライセンスではないため。）識別はクラブカラーの色チップで行います。
- 移籍情報は各カードのリンク先の報道が出典です。記事本文は転載せず、要旨のみを
  自分の言葉で日本語要約しています。
- `index.html` に `<meta name="robots" content="noindex, nofollow">` を入れて
  検索エンジンにインデックスされないようにしています。

## 公開する（GitHub Pages）

### なぜ GitHub Pages か

デプロイ回数の上限が選定基準になりました。

| | Cloudflare Pages 無料 | **GitHub Pages** |
| --- | --- | --- |
| 上限 | 500ビルド/月 | 10ビルド/時（ソフト上限） |
| 1日18更新だと | 約540回/月 → 超過 | 1回/時 → 余裕 |

当初は30分ごと（1日36回・約1,100回/月）で設計したため Cloudflare の
500ビルド/月を大きく超えていました。1時間ごとに落とした現在でも約540回/月で
超過するため、GitHub Pages のままが適切です。

出典: [Cloudflare Pages limits](https://developers.cloudflare.com/pages/platform/limits/) /
[GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

GitHub Pages の他の上限（サイト1GB、帯域100GB/月）にも余裕があります。
現在のサイトは写真込みで約4MBです。

### 手順

```bash
node scripts/setup-github.mjs <GitHubユーザー名>
```

これがフッターの連絡先を Issues リンクに書き換え、`git remote` とコミット作者を設定し、
**残りの手順（リポジトリ作成 → push → Pages有効化）を画面に表示します。**
認証を伴う操作は代行できないので、そこは自分で実行してください。

公開URLは `https://<ユーザー名>.github.io/transfer-radar/` になります。

> リポジトリは **Public** にしてください。Private リポジトリの GitHub Pages は有料プランが必要です。
> 公開されるのはこのフォルダの中身だけで、秘密情報は含まれていません。

### 公開後の自動更新

定期タスクが毎回 `node scripts/deploy.mjs` を実行します。このスクリプトは:

- `transfers.json` を検証する（JSONとして妥当か / 確度が0-100の整数か /
  **100%が「成立」以外に付いていないか** / 全案件に出典があるか）
- 検証に落ちたら **push しない**（壊れたサイトを公開しないため）
- 変更がなければ何もしない
- `git push --force` は使わない。push が失敗してもローカルにコミットが残り、次回再試行される

手動で反映したいときも同じコマンドです。

```bash
node scripts/deploy.mjs
```

### 気をつけること

- **写真の帰属表示（各カード下部）を消さないでください。** CC BY / CC BY-SA
  ライセンスの条件であり、消すとライセンス違反になります。
- **広告・課金・物販を追加しないでください。** 非営利であることが、選手の
  肖像権・パブリシティ権上のリスクを低く保っている根拠です（下の「権利関係」参照）。
- コミット作者のメールアドレスは公開リポジトリで全世界から見えます。
  `setup-github.mjs` が GitHub の `@users.noreply.github.com` アドレスを設定するので、
  実メールや会社アドレスに変えないでください。
- 履歴は1時間ごとに1コミット増えます。JSONは差分圧縮が効くので実際の増加は緩やかですが、
  数年後に重くなったら `git checkout --orphan` で履歴を作り直せます。

## 広告（アフィリエイト）の入れ方

雛形は用意済みで、**広告タグを貼るまでは何も表示されません**（空の枠も、ステマ表示も出ません。
広告が無いのに「広告を利用しています」と書くのは事実に反するため）。

### 貼る場所

`index.html` の中に広告枠が2つあります。**この2箇所以外には絶対に貼らないでください。**

| id | 位置 |
| --- | --- |
| `#adMain` | カード一覧の直後（`.grid` の外側） |
| `#adFooter` | フッターの直前 |

それぞれの `<div class="adzone__body">` の中に広告タグを貼ります。

```html
<section class="adzone" id="adMain" hidden>
  <span class="adzone__label">この先はスポンサーによる広告です</span>
  <div class="adzone__body">
    <!-- ここに広告タグを貼る -->
  </div>
</section>
```

貼ると `initAds()` が中身を検出して、枠とページ上部のステマ表示バーを自動で出します。

### 守るルール（肖像権リスクを低く保つための自主基準）

`about.html` に公開しているルールです。**破ると公開している方針と食い違います。**

- **カードの中や選手写真の隣に広告を置かない。** 上の2枠は意図的に `.grid` の外側に置いてあります
- **特定の選手の写真と、その選手のグッズのリンクを組み合わせない。** 最高裁判例が挙げる
  「肖像等を商品等の広告として使用」に最も近づく形です
- 記事の体裁をとった広告（記事広告）を載せない
- 確度スコアや掲載内容を広告主の都合で動かさない
- **各カードの写真の帰属表示を消さない。** 商用でもCCライセンスの条件は同じです

### 法令対応として用意したもの

| 対応 | 実装 |
| --- | --- |
| ステマ規制（景表法 2023年10月〜） | ページ上部の常設バー＋各広告枠の「広告」ラベルの二重表示 |
| プライバシーポリシー | `privacy.html`（Cookie・第三者Cookie・オプトアウト・免責） |
| 運営者情報 | `about.html` と `privacy.html` の冒頭 |

> アフィリエイト事業者によっては、審査時にプライバシーポリシーのURL提出を求められます。
> `https://tomohiroinoue-cmyk.github.io/transfer-radar/privacy.html` を提出してください。

### GitHub Pages の規約に注意

公式ドキュメントで「主として商取引を促進することに向けられたサイト」の
ホスティングは禁止されています。**広告はあくまで従、移籍情報が主**という構成を保ってください。
広告枠を増やしたり、カード一覧より目立たせたりすると規約違反の方向に近づきます。

## 権利関係の整理

公開にあたって確認した内容です。**法律の専門家による判断ではありません。**

### 選手写真 — 問題なし（条件付き）

Wikimedia Commons の自由ライセンス画像のみを使用しています（CC BY 4.0 / CC BY-SA 4.0 /
CC BY-SA 3.0 / CC BY-SA 2.0 / CC0）。いずれも商用・非商用を問わず再配布が許諾されています。

- **条件は帰属表示。** 撮影者名・ライセンス名・ライセンスURL・Commonsのファイルページへの
  リンクを各カードに表示しており、これを満たしています。**消すと違反になります。**
- CC BY-SA の「継承（ShareAlike）」は**改変物**に及ぶ条件です。画像を改変せずページに
  掲載するのは編集著作物への収録にあたり、サイト全体をSAにする義務は生じません。
  表示用のリサイズは形式変換の範囲です。
- フェアユース画像は自動的に除外しています（`fetch-photos.mjs` が commons.wikimedia.org
  以外のファイルと `fair use` / `non-free` ライセンスを弾く）。

### 選手の肖像権・パブリシティ権 — リスクは低いが、ゼロではない

日本ではパブリシティ権が判例上認められており（2012年 ピンク・レディー事件 最高裁判決）、
**「専ら肖像等の有する顧客吸引力の利用を目的とする」**使用が侵害にあたるとされています。
グッズ販売や広告への使用が典型例です。

本サイトは移籍報道の情報提供・論評を目的とし、広告も物販も課金もありません。
一般のサッカーニュースサイトと同じ使用態様であり、上記の「専ら顧客吸引力の利用」には
当たらないと考えられます。ただし**収益化した時点でこの前提が崩れます。**

### クラブのエンブレム・ロゴ — 使用していない

著作権と商標の両方の対象であり自由ライセンスではないため、一切使っていません。
クラブの識別はクラブカラーの色チップのみで行っています。
また、いかなるクラブ・リーグとも提携していないことをフッターに明記しています。

### 報道内容 — 問題なし

記事本文は転載せず、要旨のみを独自の日本語文にまとめ、出典元へのリンクを併記しています。
移籍金や選手名といった事実そのものに著作権は及びません。

### 残っているリスク

- 確度スコアは独自の推定であり、外れます。フッターと「確度の付け方」で
  推定値であることを明記していますが、断定的に受け取られる余地は残ります。
- 報道が誤報だった場合、それをそのまま掲載します。出典リンクを必ず併記しているのは
  読者が一次情報を確認できるようにするためです。
- 権利者からの申し出に応じる窓口（フッターの連絡先）を機能させておいてください。
